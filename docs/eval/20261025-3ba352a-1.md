## Findings

### F1 is closed on this set

All three `db-credentials` runs ended in `no_fix` with an empty patch, after one model call each; the prompts showed `-p"$MYSQL_PASSWORD"` and no literal password. In version 1 the large tier replaced both passwords in two of three runs. No run proposed a credential patch, so the new `credentials` escalation was not exercised by a live model here; the deterministic tests in the F1 plan prove it.

### F2 (unchanged). Kafka's advertised listener is read as a readiness problem (0/3)

Runs 1 and 2 changed only healthcheck timing and ended `up_failed`. Run 3 tried timing, `depends_on` conditions, more heap, and then three undeclared Kafka client timeout keys, and stopped at that patch approval. `KAFKA_ADVERTISED_LISTENERS: PLAINTEXT://localhost:9092` was in every prompt.

### F3 (confirmed). A stale log line decides `cache-port-wrong`

Across the five model runs of this scenario, the outcome follows the prompt's log lines exactly:

| Run | Log lines in the first prompt | Result |
|---|---|---|
| default 1 | `FATAL: cannot reach cache at redis:6380` | fixed |
| default 2 | the same, then `nc: bad address 'redis'` | not fixed |
| default 3 | `FATAL: cannot reach cache at redis:6380` | fixed |
| t0+small | the same, then `nc: bad address 'redis'` | not fixed |
| t0+large | `FATAL: cannot reach cache at redis:6380` | fixed |

The stale line comes from the service's first retry, before Redis was resolvable, and appears depending on start-up timing. Version 1's 1/3 and this version's 2/3 reflect how often it appeared, not a change in the models. Ordering the evidence so the final failure comes last, or dropping lines older than the last failure, is the likely fix.

### F5 (new). A code bug can end at a patch approval instead of an escalation

In `code-bug` run 1 the small tier replaced the whole `billing` environment and added `INITIALIZE_TIMEOUT`, an undeclared key, so the run stopped at a patch approval. Nothing was applied. The scenario expects an escalation, so its behaviour was not met (2/3). A person approving that patch would add a harmless timeout that cannot fix a division by zero; the risk is wasted attention, not damage. In runs 2 and 3 the small tier first raised `start_period` (an allowed timing change), and in the next round the large tier gave up with the right root cause.

### Measured time

3 h 14 min, against 3 h 13 min for version 1 and the 2.5–3 h target. `db-credentials` runs are much shorter (median 36 s, was 164 s): they stop at the escalation instead of applying a patch and waiting out the stability window. `code-bug` runs are longer (median 31 s, was 13 s), because two runs applied a timing change and redeployed before giving up.
